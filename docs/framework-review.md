# 框架审查：全局任务规则与改动边界

日期：2026-11-09。状态：改造前审查基线，以下“现状”指改造前。当前实现及验收见 [一期执行文档](unified-execution-plan.md) 和 [验收记录](phase-one-acceptance.md)。保留本文件用于追溯问题，不应把旧入口当作当前代码。

## 审查标准

框架问题是所有任务或某类任务共同依赖的运行规则存在缺口。判断依据是影响范围与行为契约，而不是文件大小、修改行数或是否出现在后端。

本审查面向当前单机服务，不预设要改成微服务或引入分布式队列。正常任务与异常任务都应遵循同一套规则。具体业务不在本次范围内。

证据分为：此前已在隔离测试库复现；当前源码已确认；需要故障或负载实验确认程度。既有测试通过只证明覆盖的场景，不证明完整机制可靠。本轮重新审查没有重新跑全部测试，也没有改变运行逻辑或操作真实店铺。

## F1：任务生命周期与恢复一致性（优先级 P1）

**全局规则**：每个请求、执行和重试预算必须具有一致、可追溯的关系。任意中断后能识别已完成、可继续、待核验和仍排队的工作，不悄悄重放未知结果。

**现状与缺口**：有 Task / Request / Execution 划分、有限重试及恢复入口。但执行终态和请求终态分开提交；恢复只检查部分执行状态，没有统一核对请求与执行的不一致。

**证据**：此前模拟结束处理中的写库失败，得到 execution=SUCCEEDED、request=DISPATCHED；恢复后仍不一致。代码入口：`已删除的 tasks/manager.py` 的 `_finish`、`recover`。

**全局改动**：把允许的状态转换、重复结束处理、请求与执行的关联更新集中到生命周期入口。清理完成后的数据库结果应成套提交；重启执行一致性核查。不得在数据库事务中等待外部关窗，也不能声称数据库事务能覆盖外部操作。

**边界**：业务只返回结果或抛出原始异常，不直接修改框架状态表；原业务内容和历史执行不能因恢复被覆盖。

**验收**：在结束、重试预算更新、取消等持久化边界注入故障；重启后无悬空请求、不重复执行已完成工作、不复活已取消任务。

## F2：资源所有权与交接协议（优先级 P1）

**全局规则**：使用共享资源的所有执行遵循申请、交付、使用、停止、释放和核验规则；旧使用者未确认停止，不得宣告安全交接。

**现状与缺口**：已有窗口容量、同店铺互斥、租约和未知状态保护；停止脚本失败后仍继续关窗，租约仍可能成为 RELEASED。异常资源缺少完整的核验与解除流程。单服务锁依赖可变的 state-dir，尚不能稳固约束同一个数据库的所有启动方式。

**证据**：此前用失败的 stop_script 回调复现：仍调用 close，资源 CLOSED/blocked，租约 RELEASED。锁路径可绕开问题由源码确认，未操作两个真实店铺服务验证。入口：[pool.py](../backend/agent_platform/resources/pool.py)、[__main__.py](../backend/agent_platform/__main__.py)。

**全局改动**：明确每一步的确认条件、失败后的拥有者、是否允许下一步及何时恢复容量；加入可追溯的人工核验命令；实例锁以受保护数据库为稳定边界。当前单机先实现可靠排他，不假设已有跨主机能力。

**边界**：资源层只管理资源，任务层决定执行终态，连接器提供实际操作证据。UNKNOWN 可以表示调度保护或日志诊断标记，绝不能生成、替换或包装错误原因。

**验收**：两个执行争用资源、开窗中取消、停止失败、关窗失败、实例重启等交叉场景；失败时不误释放容量、不误关他人窗口、不掩盖具体异常。

## F3：任务准入、并发与排队（优先级 P1）

**全局规则**：任务由统一调度入口按容量启动，不能因为积压或重复点击无界扩张执行数量。

**现状与缺口**：有持久请求队列和周期任务防重叠；派发器会启动全部符合条件的请求。五窗上限只约束窗口，不约束脚本或一般任务。缺少统一执行并发、排队容量及暂停/等待任务是否占名额的规则。

**证据**：源码确认，未做饱和负载测试。入口：`已删除的 tasks/manager.py` 的 `submit`、`dispatch`，以及 [scheduler.py](../backend/agent_platform/scheduler/scheduler.py)。

**全局改动**：定义任务并发、资源并发、等待名额和队列上限；所有手动、定时、重试、续跑请求使用同一准入机制。配置页面必须说明并发参数和调整后的生效范围。

**边界**：容量不足是等待或明确拒绝，不伪装成业务失败；不能通过给每种业务分别加限流来替代全局规则。

**验收**：大量提交、长短任务混合、等待窗口、暂停、连续重试、重启后积压；运行数量有界，任务不会因重试占满全部名额而无限饥饿。

## F4：执行隔离与故障范围（优先级 P1）

**全局规则**：一个任务的错误或阻塞不能停止其他任务的调度、超时检查和服务控制；共享存储等全局故障则必须明确报告并执行统一策略。

**现状与缺口**：普通 handler 异常已有捕获，脚本有受管进程；但 Python handler、工具回调与调度共用事件循环，阻塞调用可能卡住全局；单条调度配置异常也能逃出服务主循环。

**证据**：此前 `first_at` 非法值通过配置后触发 scheduler TypeError 已复现；主循环没有单项调度隔离由源码确认。同步阻塞影响的量级未做压力实验。入口：[__main__.py](../backend/agent_platform/__main__.py)、`已删除的 tasks/manager.py`、[registry.py](../backend/agent_platform/tools/registry.py)。

**全局改动**：明确异步回调的非阻塞约束及阻塞工作执行边界；按任务隔离调度错误；定义超时和取消在不同执行方式下的实际能力。不能仅用更大范围的 except 把异常吞掉。

**验收**：任务 A 阻塞、报错或停止失败时，任务 B、日志查询和停止入口仍按约定响应；全局存储失败时不虚报局部成功。

## F5：服务停止与重启协议（优先级 P1，部分已实现）

**全局规则**：停止是服务级过程，覆盖新请求、队列、运行、等待资源、暂停和清理中的全部执行。

**已实现**：停止时拒绝新任务、停止派发；已有执行可以申请窗口；等待时长和到期策略可配置；收尾期间保持状态和日志查询；重启启动器等待旧进程退出。

**仍有缺口**：开始收尾后 API 拒绝所有非 shutdown 的修改，无法从页面结束一个卡住的执行或把本次等待升级为取消；恢复时仍缺少 F1 的一致性核查及 F2 的完整资源核验。默认继续等待意味着没有自然结束条件的任务可能持续等待，需要明确可干预方式。

**证据**：源码确认。入口：[server.py](../backend/agent_platform/api/server.py)、`已删除的 tasks/manager.py`、[start.ps1](../deploy/start.ps1)。

**全局改动**：区分禁止新增工作的命令与允许协助收尾的控制命令；记录本次停止进度、策略及人工干预；恢复完成后才允许新派发。

**验收**：上述各种执行状态混合存在时停止服务，验证队列保留、已有任务完成、人工结束、资源清理失败、重启核验，不能只测空服务重启。

## F6：数据与日志的容量和访问边界（优先级 P2）

**全局规则**：日志或历史数据增长不能无限占用任务内存，也不能让一次查询拖住所有任务。证据必须持久化，容量管理须可配置、可审计。

**已实现**：脚本双流分段入库、有界预览、日志数据库分页与原文查询。

**仍有缺口**：状态接口仍全量读取历史；读日志、写日志、任务状态共用连接及同步锁；缺少日志归档、保留期限和磁盘容量策略；CLI 仍缓存完整返回。数据库结构也缺少显式版本迁移机制。

**证据**：源码确认这些结构存在，性能阈值、磁盘故障和迁移能力尚需专项验证。入口：[store.py](../backend/agent_platform/database/store.py)、[logs](../backend/agent_platform/logs/__init__.py)、`已删除的 tasks/manager.py` 的 `snapshot`。

**全局改动**：分离列表摘要与详情，明确数据库读写调度及有限缓冲；统一大返回值处理；建立备份、迁移和日志保留策略。不要为了异步写入引入无限队列，也不能为了减压静默丢弃错误原文。

**验收**：日志高产出同时查询、长历史状态查询、写库失败和容量不足；验证任务响应、内存上限、原文完整性和可恢复性。

## F7：配置与扩展接入契约（优先级 P2）

**全局规则**：所有任务通过统一入口注册、校验和读取配置；一次执行使用哪些配置必须确定；框架运行态不依赖业务自行补约束。

**现状与缺口**：配置校验分布在管理页面、manifest 加载和 manager 中；任务定义同时写入文件及数据库，异常回滚不等于强杀时的一致性；handler 直接收到含 manager/store 的上下文，缺少受限的框架操作边界。

**证据**：源码确认。入口：[catalog.py](../backend/agent_platform/employees/catalog.py)、[manifests.py](../backend/agent_platform/settings/manifests.py)、[context.py](../backend/agent_platform/executions/context.py)。

**全局改动**：明确配置权威来源、版本、生效点及恢复规则；将完整校验放在统一入口；限定业务经由上下文调用任务、资源、日志能力，不直接操作生命周期表。保持现有目录职责，不要求为每个配置项再建一层服务。

**验收**：页面、清单和代码注册对同一非法输入给出一致拒绝；配置修改不改变既有执行的输入；崩溃后文件与数据库按明确规则收敛。

## F8：外部操作、超时与重试语义（优先级 P1）

**全局规则**：请求等待超时不等于操作失败；框架必须区分可安全重试、已经完成和结果尚待核验，避免全任务重试重复执行外部动作。

**现状与缺口**：请求有 operation_key，失败重试有次数预算，未知窗口会阻止自动业务重试。但一般工具/外部调用尚无统一的重试安全声明、操作记录和结果核验机制。API 等待超时后协程可以继续执行，缺少以操作编号查询最终结果的完整协议。

**证据**：源码确认。入口：[server.py](../backend/agent_platform/api/server.py)、[registry.py](../backend/agent_platform/tools/registry.py)、`已删除的 tasks/manager.py`。未对真实外部业务做重复动作实验。

**全局改动**：将操作身份、结果记录、超时与重试安全性作为工具/连接器接入契约；非幂等动作不能仅因捕获到异常就重跑整个任务。接口返回需能关联后续结果查询。

**边界**：框架不能仅凭本地日志保证外部操作“恰好执行一次”；无法核验时保留实际错误和操作证据，暂停自动重放。

**验收**：外部已执行但响应丢失、客户端断开后操作完成、重复提交、重启后收到迟到结果；确保不凭超时推断失败，不因重复点击扩大副作用。

## 代码布局结论

现有 tasks / executions / scheduler / resources / runtime / connectors / logs / settings / database / api 的目录划分可继续沿用。主要不足是共享规则尚未统一落实，不是目录数量不够。

当前已采用的职责：queueing 负责生命周期与调度决策，tasks 负责定义和注册；resources 负责资源所有权和交付确认；runtime 负责执行隔离及进程控制；connectors/tools 负责调用协议和证据；settings 负责统一校验和版本；database 负责持久化和原子提交；logs 负责日志存取及展示投影；api 调用这些入口，不直接变更生命周期状态。

新增抽象应服务具体不变量，不为了“框架化”堆叠异常包装、重复存储或通用流程解释器。
