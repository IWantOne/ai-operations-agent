# 店铺来源与日志规范 v1

状态：已实施。制定日期：2026-11-09。

适用范围：店铺资料、工作台日志列表及 `/api/logs/query`。本规范定义用户术语、事件登记、查询和展示规则；不改变执行状态、资源归属、重试或清理策略。

## 1. 店铺资料的三个独立概念

| 用户字段 | 定义 | 当前值或示例 | 数据字段 |
| --- | --- | --- | --- |
| 店铺来源 | 工作台从哪个外部系统获得店铺资料 | 紫鸟 | `provider=ziniao` |
| 平台 | 店铺开展业务的经营平台及站点 | 亚马逊-美国、沃尔玛-全球 | `platform` |
| 连接方式 | 工作台访问来源系统的技术方式 | WebDriver、CLI | 账户连接的 `mode` |

所有通过紫鸟读取的店铺，其来源均为紫鸟。WebDriver 和 CLI 不属于店铺来源；亚马逊也不因此成为工作台的店铺资料来源。以后接入其他来源时必须显式登记 provider，不能根据店铺名称或经营平台猜测。

当前单一来源内以紫鸟店铺 ID 关联任务，任务的 `input_data.shop_id` 是现有关联字段；店铺名称仅用于显示。店铺详情汇总所有员工当前关联该 ID 的任务。没有关联任务不等于没有店铺或读取失败。若未来支持多来源，必须先将关联键升级为 `(provider, shop_id)`，不能直接混用不同系统的 ID。

## 2. 日志字段词典

| 界面名称 | 回答的问题 | API 字段 | 规则 |
| --- | --- | --- | --- |
| 时间 | 何时记录 | `occurred_at` | 存储 Unix 秒，界面使用本地时间 |
| 记录模块 | 谁记录了这件事 | `module` | 工作台系统、任务执行、脚本运行、工具调用、窗口管理、紫鸟连接 |
| 事件类型 | 属于哪一类活动 | `event_type` | 见下一节；互斥的主类型，不表达成功失败 |
| 事件 | 具体发生什么 | `event_label`、`action` | 中文名称为显示标签，原事件代码保留在详情 |
| 数据来源 | 此事件明确涉及哪个外部数据提供方 | `provider` | 当前仅紫鸟；未明确登记则为空，显示“未标注”，不推断 |
| 级别 | 记录者给出的严重程度 | `level` | 调试、信息、警告、错误、严重错误；不是业务最终结果 |
| 诊断标记 | 是否存在特殊核验事项 | `category`（兼容字段） | 当前仅 `UNKNOWN` → “资源结果未确认”；不是通用分类 |
| 关联对象 | 与什么记录有关 | `task_id`、`execution_id`、`borrow_id`、`call_id` | 只使用实际保存的标识；店铺标识可从明确的 `shop_id/store_id/browser_id` 读取 |
| 结果与内容 | 实际取得什么结果或错误 | `content` | 保留证据，按第 5 节展示 |

`source` 是旧 API 中的**存储表名**，不再用作界面的“来源”。它仅用于兼容筛选、定位存储记录以及 `(source, id)` 唯一标识。不得把 `content.source`（例如调度触发来源）误当成 provider。

来源与模块的例子：紫鸟 WebDriver 响应属于“紫鸟连接”模块，数据来源“紫鸟”；窗口申请入队属于工作台的“窗口管理”模块，其日志由本地调度记录，即使操作的店铺来自紫鸟，也不把本地调度结果冒充紫鸟返回。

## 3. 事件类型与登记

| 标识 | 名称 | 范围 |
| --- | --- | --- |
| `system` | 系统运行 | 服务停止、工作台 API 异常 |
| `settings` | 配置变更 | 时间策略、重试策略保存 |
| `task` | 任务执行与控制 | 执行开始、结束、暂停核验、启停任务、执行申请窗口 |
| `schedule` | 任务调度 | 请求入队、跳过重叠计划、重启期间错过的计划 |
| `window` | 窗口借还 | 窗口申请、取得、归还、回收、归属冲突及开关窗口 |
| `connection` | 接口通信 | 连接器原始返回、异常、中断、端口探测 |
| `script` | 脚本运行 | 脚本启动、管理、返回、超时、停止、异常 |
| `tool` | 工具调用 | 工具开始、返回、异常 |
| `custom` | 未登记事件 | 尚未纳入词典的历史或业务自定义事件 |

准确的事件代码、中文名称、模块、类型和来源映射统一维护在 [catalog.py](../backend/agent_platform/logs/catalog.py)。后端返回 `definitions`，前端据此生成筛选项，不再维护第二套词典。

连接器事件只由适配器基类写入：CLI 与 WebDriver 必须声明同一组事件槽位（开窗、关窗、归属冲突、原始返回、异常、中断），适配器只实现传输层原语，不各自决定写哪条日志。少声明一个槽位时适配器类定义即失败。

各模块的日志统一从 [logs/writer.py](../backend/agent_platform/logs/writer.py) 的 `LogWriter` 写入：一张表一个 writer，由拥有该事实的模块持有；写入前按 catalog 校验动作，没登记的动作当场报错。模块内的任务和业务代码不直接调用 `store.log`。

未知事件必须继续可查，名称回退为实际 action，类型显示“未登记事件”；模块可回退为其存储模块，provider 留空。不能根据错误文本关键词猜测事件类型、来源或故障原因。

新增框架事件时，开发者必须同时登记：存储表、稳定 action、中文事件名、记录模块、事件类型、明确来源或空值、级别选择、关联标识、证据字段，并补充对应查询或展示回归验证。动态业务事件可以先保留原代码，但需要正式产品展示时必须补充登记。

## 4. 级别与诊断标记

- DEBUG / 调试：内部诊断细节。
- INFO / 信息：普通过程或收到的返回。INFO 不证明业务成功；收到 HTTP 响应也不证明调用成功。
- WARNING / 警告：需要关注但不等于已失败。
- ERROR / 错误：记录者观察到的操作异常。
- CRITICAL / 严重错误：记录者明确判断影响服务可用性的严重问题。

界面忠实显示已记录的级别，不根据事件标签或返回码偷偷重写历史级别。业务是否完成以 execution_info 的最终状态为准，不能依据单条日志、进程退出码或单个请求完成事件判断。

`UNKNOWN` 只在 resource_log 的 CLOSE_FAILED、OPEN_CLEANUP_FAILED、OPEN_INTERRUPTED、OWNERSHIP_CONFLICT 事件上派生。它表示事件发生时资源结果需要核验，不代表资源目前仍异常，也不能替代该事件的实际原因。其他事件留空，不能将空值理解为正常或成功。

## 5. 列表与详情展示

列表优先展示中文事件名和可核对的结果摘要，按时间倒序。事件类型、模块、数据来源、级别独立筛选；诊断标记保留为特殊筛选。正常返回和错误均可查询，不删除、不静默隐藏正常记录。

摘要规则：

1. 有明确 `error` 时优先展示原错误。WebDriver 返回正文中有非空 `err` 时必须展示，不以“调用失败”代替。
2. WebDriver 响应显示实际 operation、HTTP 状态、紫鸟 statusCode；仅在列表字段确为数组时显示条数。文案用“收到响应”，不把 statusCode=0 或 HTTP=200 推导为任务成功。
3. 缺少返回码就显示“未提供”；正文不是可解析对象时保留实际正文，不虚构返回结果。
4. 脚本返回保留退出码及 stderr/stdout；非零退出码不包装为成功。通用事件展示实际 message/reason/内容，未知结构回退原文。
5. 不依据 UNKNOWN 或其他分类生成错误原因。超长摘要可折叠，但必须提供完整内容和存储原文。格式化只是展示行为，不更新数据库 content。

展开详情保留：存储表与记录 ID、原 action、事件类型、数据来源、调用标识、异常堆栈、完整格式化内容以及存储原文。原始异常、后续清理失败分别保留，不覆盖或合并为一个泛化错误。

示例：读取店铺列表的实际响应包含 HTTP 200、statusCode 0、74 个 browserList 元素，列表显示“收到响应 · HTTP 200 · 紫鸟返回码 0 · 返回店铺 74 家”。这是一次账户查询记录，未绑定任务时关联为空是合理的，不人为补任务 ID。

所有写入日志的凭据应先脱敏，再保存证据；所谓“存储原文”是已保存的脱敏文本，不意味着允许保留密码、App Secret 或令牌。当前 WebDriver 实现会遮盖配置密码回显；其他凭据字段接入时需同步扩展脱敏和验证。本次不会重写历史日志，也不宣称历史所有字段已经完成全面脱敏审计。

## 6. 查询与兼容

`GET /api/logs/query` 支持 `module`、`event_type`、`provider`、`level`、`execution_id`、`q`、`since`、`until`、`page`、`page_size`；保留旧 `source` 和 `category=UNKNOWN`。筛选在数据库 UNION 查询中执行后计数、分页，不能先取一页再前端过滤。

新增字段均为查询元数据，不迁移历史表、不修改 content、不制造第二层异常。历史已知事件按同一词典解释；未知事件保留原文。默认每页 50 条、上限 100 条。翻页沿用查询截止时间，刷新回第一页读取最新数据。兼容 `/api/logs` 只用于旧时间线入口，不应当作完整日志查询接口。

## 7. 验收标准

- 紫鸟店铺来源显示“紫鸟”，经营平台和连接方式独立展示。
- 紫鸟响应在“紫鸟连接 / 接口通信 / 紫鸟”中可查，不再与窗口借还混为一个来源。
- 同一个事件的分类不会改变原内容、级别或执行结果。
- 非零返回码和具体错误不会被成功摘要掩盖，未知事件不会丢失。
- 模块、类型、来源筛选与跨表分页一起生效；旧参数兼容。
- 列表可读、详情保留诊断证据，未关联任务的账户查询不制造虚假关联。

验证入口：本项目不维护自动化测试套件，日志展示按第 5 节手工核对，或走 `verification/workbench.py --manual`。


## 8. 脚本流式输出

`runtime_log.script_output` 登记为“脚本运行 / 脚本运行”，来源留空，级别 INFO（写入 stderr 本身不代表执行失败）。每次脚本调用生成独立 call_id，输出、启动和结果均以此关联，并保留 execution_id。

stdout/stderr 并行读取，每次最多 16 KiB，读到即写入并提交数据库，不等待换行或进程退出，不设置无界缓冲队列。字段为 stream、sequence（平台接收顺序，不声称跨管道的真实写入先后）、byte_offset（各流字节偏移）、text（UTF-8 增量解码文本）、raw_base64（可精确还原原始字节）。非 UTF-8 字节在文本预览中使用替换符，原字节不丢失。

`script_result` 仅保存退出码、各流总字节数和预览截断标记，不再重复整段输出。`ctx.script` 返回 stdout/stderr 各最多前 64 KiB 的预览、stdout_bytes/stderr_bytes、stdout_truncated/stderr_truncated 及 output_call_id。小输出兼容原返回；大输出调用方必须检查截断标记，不能把预览当完整结果。完整输出通过日志列表的“调用 ID”或 `/api/logs/query?call_id=...` 分页读取，按 sequence 重组，禁止为了返回结果再次全量拼进内存。

Python 子进程设置 PYTHONUNBUFFERED=1 和 PYTHONIOENCODING=utf-8；其他程序仍需自行及时 flush。平台只能持久化已从管道读取的内容，不能保证强杀前尚在子进程或系统管道中的字节已经入库。数据库写入失败时终止所属脚本并传播具体异常，不继续运行且静默丢日志。
